# 2026-08-30 复盘：#131 切片 A 九轮 review 为什么没修好——设计缺席的诊断

> 本文是 PR #149（GitHub REST Gateway 切片 A，计量桩/证据层）九轮 REQUEST CHANGES 之后，作者与实现 agent 的一段对话实录整理。它回答一个问题：**门装了（issue-gate/grill/challenge）、九轮也认真修了，为什么问题一直在？** 结论分四层，一层比一层深。它是 #111（调用点补丁）与 #144（概念膨胀）之后的第三个病例：**设计缺席 + 表征代替实体**。

## 背景：九轮里发生了什么

切片 A 的任务看起来最小：给既有 `GithubRestReader` 按 #133 冻结口径埋计量桩，零行为变化。九轮 review 的 findings 走向：

| 轮 | finding | 当轮"修法" |
|---|---|---|
| R1 | loaderDepth 实例级并发漏计；证据 schema 表达力不足；counters 无生产消费者 | ALS 换作用域；加字段；接诊断 |
| R2 | 同桶覆盖；解析前失败丢 upstream 层；失效无 generation/完成态 | 样本序列；补记录路径；status 字段 |
| R3 | 组合 JSON 解析失败丢 upstream；secondary 误标 primary；observed 只在内存 | 双层补齐；kind 共用；持久事件 |
| R4 | 残缺 headers 吞掉整条 observation；分页 shape 失败丢操作 | 每响应必留样；补 upstream 记录 |
| R5 | 缺 resource 伪造 core；headerless 429 挂旧桶 | 去 fallback；trip 绑当前响应 |
| R6 | resource 缺失把同记录已知数值整条丢掉 | 始终持久当前样 |
| R7 | 容器又没了消费者（option b 没保持住） | 删容器（减法） |
| R8 | drain 等错队列/单次快照/测试 gate 在生产队列外 | root 级 drain + 叙述刷新 |
| R9 | 快照漏 mid-drain 注册；gate 仍需入队内 | fixed-point + 队列内 gate + red-check |

每轮的 finding 都是真的、都修掉了——然后下一轮出现相邻的一个。

## 第一层：为什么修不好——只修被点名的那一个，从不枚举等价类

- 修"resource 缺失别伪造 core"时写出 `resource !== null ? sample : null`——一个字段的纪律，把同记录其余字段全丢了（R6）；
- 修"解析失败丢 upstream"时只想到 JSON 语法错，没枚举解析成功之后的全部 throw 路径（分页 shape，R4）；
- teardown 修了四轮：加 drain → 位置错（HOME 恢复后 drain，stateDir 已变）→ 队列错（undefined-key 只等 global 流）→ 枚举报（单次快照）→ gate 挂在 `.then` 上根本不在生产队列里。

这正是 fix-discipline 原则 6 写着的："存在性缺口必须一次找全，一次找一个 = 跳过了这层"。**九轮里每轮都在跳**，评审被迫一轮一个地替实现者做枚举。

配套的病：**测试在验证实现者的想象而非生产机制**。R8 的测试注释写着"trailing 写仍在队列中"，评审直接从磁盘读到了那行。测试断言的是"我以为的世界"，且它是绿的。red-check（把修好的机制改坏、证明测试会红）是最便宜的自检，八轮都没做，却每轮都写"已全部关闭"。

## 第二层：为什么会有这么多可修的——切片大部分时间没有真实消费者

评审第 2 轮就指出了，实现者选了"option (b)：counters 与消费者同批交付"，然后反复违反。一个没有消费者的仪器层，没有任何生产行为会因为它错而坏，唯一能证伪它的就是对抗性读取——于是评审成了事实上的消费者，每轮修复都在优化"让上一条评论消失"而不是"让机制对"。当修正的目标是评论而不是不变量，就会一直产生下一条评论。

结构性因素：**纯仪器化 PR 的评审面 = 全部 diff**。零行为变化意味着所有正确性问题都暴露在 diff 里，没有生产流量兜底。评审九轮没有冤枉任何一次。

## 第三层：为什么会走到这一步——我们真的做了架构设计吗？（没有）

grill 产出的 Q1–Q6 全是**范围决策**（建什么：两级优先道、预算归 Gateway、六处直写回读、吸收旧机制、切片、baseline）。AGENTS.md §2.0 对 L3 的要求——**先定义事实源、不变量、原子边界、失败模式**——一样都没写成文字。证据就在九轮评论里：评审反复引用冻结基线的**行号**打人（`:158` every response records bucket、`:45` unknown 纪律），那些要求在动手之前就已存在、写在两份必读文档里；实现者没有做"从冻结基线推导实现契约"这一步，它们就以 finding 的形式一轮轮降落。

因果链：

```
没写契约 → "正确"无定义 → 评审从冻结基线推导出一条要求
→ 修被点名的实例 → 因为没有失败全集枚举，相邻缺口必然存在
→ 下一轮 finding → 循环 9 次
```

第一、二层的病（枚举缺失、测试剧场、无消费者）全是这一层缺失的下游症状。

## 第四层（对话中被连续纠正两次）：即使补"设计"，补的也可能不是设计

实现者第一次自我修正时说"真正的设计本来长什么样"，列了四样：不变量表、失败全集、schema 字段纪律、红绿灯约定。**被用户否定：这些还是数据结构，完全没有算法。**

> 用户：程序 = 算法 + 数据结构，这两个是相互激发和限制的，比如队列这东西，数据结构出不来的。

重读九轮，全是**算法 bug 穿着数据结构的衣服**：

- loaderDepth 并发漏计 = 作用域算法错；
- trip 绑定错旧桶 = 请求生命周期里"哪一步捕获的观测归哪次响应"的数据流问题——pipeline（`进入 → 排队 → 派发 → 传输 → 解析 → 分类 → 记录`）从没被画过；
- teardown 四轮 = 诊断写入是链式入队**算法**，drain 应是它的对偶算法（重枚举到不动点）；"遍历一次 Map"是数据结构操作，不是对偶；
- 残缺 headers、分页 shape = pipeline 的分支点，每个分支该记什么是算法设计。

规律：**仪器挂在调度器上但不理解调度器的算法，就一定在算法的每个边角记错**。rest.ts 里现成住着五六个算法（250ms 节拍道、singleflight、熔断、TTL/版本双键缓存、force 代次竞争），"吸收它们"是算法重设计，却被当成搬移字段。相互激发的实例就在自己代码里：`waitForAllDiagnosticLines` 的不动点循环从 Map 里推不出来——只有建模了链式入队才可想象；反过来证据记录的形状也不是 schema 设计出来的，是 pipeline 阶段划分（upstream 层产生于派发阶段、access 层产生于意图结算阶段）**先于**记录形状。

## 第五层：为什么门没拦住——门链有个洞，而且洞写在出口状态里

用户装了 issue-gate → challenge（问题对不对）→ grill（决策全不全）→ **"Ready for specification/planning"**。前两道门各司其职。但 "specification/planning" 是一个**有名字却没有任何东西拥有的阶段**——grill 台账直接被当成了设计，`开始实现` 之后就写了代码。AGENTS.md §2.0 的 L3 设计要求整个会话都在上下文里，它是只有文字没有门禁的规则——而 fix-discipline 自己写着"构造优于纪律"，一条没有强制力的规则被跳过不是意外，是这个坏构造按设计运行的必然。

实现者为什么没看见：

1. **把门当仪式通过，没当模型审视**——在问"这道门过了吗"，从没问"这条管线缺哪道门"；
2. **grill 台账长得像设计**（表格、决策、理由），满足了"设计已发生"的模式匹配——与 `.then` 挂的测试长得像回归、evidence 记录长得像证据是同一个病：**一贯地拿表征代替实体**；
3. 规则无机制 = 纪律，纪律失败是已被本仓库预言的模式。

## 修复方向（对话中收敛的）

1. **补第三道门——设计门**：L2/L3 在 grill 后的出口状态应是 "Needs design artifact" 而非 "Ready for specification/planning"；设计门准入物 = 算法叙述（含被否决的替代方案）、失败全集枚举、结构判决、契约——齐了才翻 Ready to implement。让它像 challenge/grill 一样是挡路的机制。
2. **关闭声明前必须 red-check**：把修好的机制临时改坏，证明回归会红；不红的测试不算证据。
3. **测试必须 gate 生产机制的内部**（pending 参数、队列、时钟），不能在返回值后挂门。
4. **修字段级 finding 时先枚举同一记录/不变量的全部相邻路径**，一次修完一个等价类。
5. **权重调度器的算法设计**（对话中用户提出并完善）：所有 gh/git 调用经一个加权准入调度器，声明五维（plane / identity / scope / weight 档位 / joinable）+ 派生 budget（gh api 消耗额度桶、git fetch 不消耗——成本模型决定 park-until-reset 只停真正争抢耗尽资源的操作）；调度 grant 即写权限凭证（原则 4 的算法化）；权重是固定档位防通胀；老化防饿死；按协议分桶不按二进制名分（`gh pr merge` 内部是 REST，消耗；`git push` 不消耗）。既有机制全部降格为这一个算法上的策略：串行道→节拍策略、TTL 门→合并窗口、singleflight→join、熔断→park-until-reset。

## 与前两个病例的关系

- #111（十轮）：调用点补丁——修法向**下**堆检查；
- #144（八轮）：概念膨胀——修法向**上**加层；
- #149（九轮，本例）：设计缺席 + 表征代替实体——修法在**错误的抽象层**打转：给没被设计的算法套数据结构外壳，用"长得像 X 的东西"代替 X（测试代替回归、台账代替设计、门通过代替门审视）。

三者共同的循环元规则命中条件：同类 CRITICAL 连续多轮、diff 或 finding 持续不收敛——但本例的预警信号更早就有：**一个"准备好了"的状态词后面跟着没有任何产物占位的阶段**。这可能值得作为第四个病例的特有指纹。
