# 自动 ready 判定、批量开发与依赖账本设计

Issue #9 采用服务端事实判定、客户端批量编排、GitHub 幂等账本三层设计。仓库快照一次读取全部 issue，直接依赖只取 `## 依赖` 中的 `Blocked by #N`，再用同一快照内 issue 的实时状态解析。只有 OPEN、契约完整、无 OPEN/UNKNOWN 直接依赖、且状态机下一步为 `develop` 的 issue 才标记为 `ready`；已开发、恢复、Review、合并流程均不进入自动首发。列表支持勾选单项或一键选择全部 ready issue，并在一次汇总确认后逐项启动，单项失败不吞掉其它结果。

批量执行不能信任列表快照。每个 issue 仍走现有快照授权，启动请求增加 `automatic: true`，服务端在创建 worktree 前强制刷新 issue 详情、重跑契约与依赖门槛。这样即使列表过期、契约刚被删改或依赖状态未知，也会 fail closed；人工单项开发仍保留原有显式授权语义。

依赖账本在仓库刷新发现“原有直接依赖全部 CLOSED”时维护。先检查带稳定依赖编号 marker 的流水评论；不存在则发布“依赖 #N 已完成，本 issue 解锁”，然后 PATCH 正文的 `## 依赖` 为 `依赖: 无(原 Blocked by #N 已完成，自动更新)`。评论先于正文，确保评论失败时正文不前进；正文失败时下次通过 marker 跳过重复评论并重试 PATCH。解析器把 `依赖: 无` 视为权威，因此历史编号不会重新形成依赖边。任何维护失败会显式返回到列表，不伪造成功，也不改变实时 ready 判定。
