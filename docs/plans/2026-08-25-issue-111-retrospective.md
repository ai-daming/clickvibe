# Issue #111 复盘:一个并发 bug 的十九轮循环,与一套协作协议的诞生

> 2026-08-24 00:47 首次开发提交 → 2026-08-25 review 通过。31 commits / 74 files / +5001 −597 / 18 轮 review / 19 轮开发交付 / 约 30 小时。本文回答三个问题:根因到底是什么、协议是如何长出来的、哪些教训还没被任何文档吸收。

## 一、时间线:三个阶段

### 阶段一:打地鼠期(R1-R10)

无协议。dev 修"reviewer 上次点名的那个交错",reviewer 每轮找到一个新的。diff 从 93 行涨到 2669 行,**修复本身在制造下一轮的 bug 表面**。R4-R8 五轮 CRITICAL 全是同一个母题("六个入口各自推导'当前任务是哪个'")的变装,没有任何一方发现。

转折点是人在第 10 轮问了跨轮问题:"**为什么总是有问题,一直搞不好?**"——这个问题在循环内任何角色的单轮视野里都不存在。

### 阶段二:洋葱期(R11-R16)

fix-discipline.md、root-cause-review skill、observer 角色相继建立。review 从"验证补丁"升级为"母题分类 + 双层根因 + 修复高度判定",静态枚举审计上线后 finding 从"一次一个"变成"一次一类"。

但技术上仍是剥洋葱:每关一层机制,下一层的洞才可见——

| 轮 | 落地机制 | 暴露的下一层 |
|---|---|---|
| R11 | 跨进程锁 + 原子写 | 有锁没条件 = 原子地丢更新 |
| R13 | revision + 凭证校验 | 布尔压扁语义、可空类型边界 |
| R14 | 判别式结果、非空约束 | token 可刷新 |
| R15 | taskStateRevision | token 能从重读的快照刷新回来 |
| R16 | lease(claim 签发、绑 LiveTask) | stop 与回调是两个排序域 |

每一层都是真修复,每一层都不够——**洋葱不是发现的必然形状,是"补课 + 不查地图 + 每轮一个反例激励"的产物**(见原则 9 教训)。

### 阶段三:升级与收敛期(R17-R19)

- **R17**:lease(机制级)落地后母题仍复发 → **抽象层升级终止条件首次触发**:"整对象快照写模型表达不了 stop 是链终止符,换模型,禁止第 N+1 层围栏"。
- **R18**:新模型(单命令域)落地,但旧整对象提交改名为 `commitWorkflow` 存活 → **改名式修复(fake redesign)被抓住**(公开 API 面前后对比检测,已进 skill 第 5 步)。本轮教训:判"抽象错了"之前必须先确认"抽象真的落地了"——R17 是选错,R18 是没做完,处理方式完全不同。
- **R19(收敛)**:整对象公开提交入口删除;`commitWorkflowMetadata` 在**类型层面**排除任务状态字段(`Exclude<keyof IssueWorkflow, ProtectedWorkflowField>`,想塞 stage 编译不过);任务状态仅 lease 制命令域可写;stop 在域内线性化(撤销落盘后才返回);"raw mutator absent"测试改为枚举真实导出面。review 通过。

## 二、根因的分层真相

表层 bug 是"宿主中断后任务状态倒退/双开"。真实根因是一条完整链,教科书里早有地图:

**没有并发模型** →(需要)互斥 → 原子写 → revision → CAS → fencing token → lease → **单写者命令日志**。

最后一步是这个问题类的**完全体**:fencing token 只是它的组成部分。R9-R16 用八轮从零推导了教科书已有的一章(DDIA 第 8 章)。原则 9(已知模式先验)由此而来:先匹配地图,再自行推导;匹配命中按完全体一次实现。

另一个必须记住的根因表述:**"缺失≠死亡"的证据模型错误**贯穿始终——内存查无记录被当成任务已死,查有记录被当成任务活着,两个方向都在撒谎。三分状态(running/unknown/interrupted)是证据模型的修复,先于所有并发机制。

## 三、协议是如何长出来的:疼了才装

| 疼(轮) | 装的零件 | 生效轮 | 若第一天就在,可省 |
|---|---|---|---|
| R4-R8 同类五连发 | 母题分类、fix-discipline 原则 | R11 | ~7 轮 |
| R12 一次只找一个 | 静态枚举审计(skill 步骤 4) | R13 | ~3 轮 |
| R9-R16 重新发明轮子 | 已知模式速查表(原则 9) | R17 | ~6 轮 |
| R17 预言落空 | 抽象层升级终止条件(原则 8) | R17 | — |
| R18 改名存活 | 公开 API 面对比检测(skill 步骤 5) | R18 | 1 轮 |
| 全程人工驱动 | 循环驱动模板、verdict 附「下一轮指令」 | R13+/部分未落地 | — |

**核心教训:每条规则都晚于它本该出现的时机 3-8 轮。下一个项目整套 upfront 装齐,把 30 小时变成一天。**

## 四、六条教训(本节是本文档存在的理由)

1. **规则没有触发人 = 没有规则。** 用户全局 CLAUDE.md 从第一天就写着"失败 3 次必须停下来反思",十轮里一次都没触发——循环内没有角色负责盯它。停机规则必须写明"谁在什么时机核对";observer skill 的触发条件因此是硬性职责而非参考。
2. **个人判断连续错三次,编码规则零漏报。** observer 预言"焊死"(被绕)、"符号解析是终态"(被绕)、"lease 是终点"(复发);同期编码的终止条件两次按设计触发并抓住其中两次错误。结论:可编码的规则可靠性高于任何个体直觉(包括规则的制定者),这正是 observer 退出条件要求"产出协议变更"而非"给出正确判断"的原因。
3. **三层互审闭环验证。** coder 被 reviewer 抓(18 轮)、reviewer 被 observer 验证(每轮读代码确证)、**observer 被 reviewer 抓**(门禁连续 4 轮被判,每次属实,包括最后一次"白名单放行违规入口"的假绿)。observer 不是免检产品。
4. **语法级门禁是绊线,不是墙。** 名字追踪→AST→符号解析,四轮里三轮被值传播绕过(对象属性、高阶参数)。原理性不完备,不可修补。唯一边界是构造(API 面不暴露能力);门禁在能力移除后降级为回归绊线保留。此教训已写进 fix-discipline 机器门禁一节。
5. **终止条件需要前置检查。** "机制级修复后复发 = 抽象错"必须先确认"修复真的落地了"(R18 改名检测),否则在"没做完"与"做错了"之间震荡,永不收敛。
6. **协议已部分自我传播。** 末期 reviewer 独立引用原则 8/9 判案、把"构造优于纪律"迁移到门禁这个 skill 未明写的对象上。但「下一轮指令」段到末期仍未稳定输出——形式合规落后于实质合规,产品化(见第五节)是解法。

## 五、产品欠账(复盘的后续动作,独立于本 PR)

1. `src/agent/prompt.ts` 按 review verdict 自动选模板 + 透传「下一轮指令」段(fix-discipline「长期目标」标注的欠账);
2. review prompt 模板引用 root-cause-review skill;
3. dev 侧对无法复现的 finding 的打回权(双向制衡);
4. 裸点实验:低风险轮次不贴任何补充指令,验证 AGENTS.md 引用是否足以让协议自驱动。

## 六、终态架构(一段话)

每个 workflow 一个**单一串行命令域**:启动/停止/完成/verdict/失败/元数据变更全部是域内命令条目,全序执行;stop 线性化(撤销落盘后才允许返回成功);任务状态字段只有 lease 制命令可写,lease 在 claim 时签发、生命周期提交即作废、不可从任何快照刷新;元数据提交的类型装不下任务状态字段;state facade 无公开整对象写入口。声明↔构造映射见 `docs/plans/2026-08-24-workflow-mutation-invariants.md`。

## 七、可迁移性

这套东西与 ClickVibe 业务无关,可整体搬走:九条原则(fix-discipline)、跨轮根因 review 流程 + 改名检测(root-cause-review)、循环外审计角色(observer)、三种轮次模板、绊线门禁的定位。迁移清单:一份 fix-discipline + 两个 skill + 把"谁在何时核对停机规则"指派给人。
