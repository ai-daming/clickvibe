# 修复纪律与并发不变量(fix discipline)

> 本文档从 issue #111 的十轮 review 循环复盘提炼。它不是风格偏好,而是约束:凡涉及状态、并发、持久化的修复,违反即返工。配套的 review 流程见 `skills/root-cause-review/SKILL.md`。

## 为什么需要这份文档

#111 用十轮 review 修一类并发 bug,每轮 CRITICAL 都被"精确修掉",但累计 diff 从 93 行涨到 2669 行,问题从未消失。复盘结论:

> 每一轮修的都是"reviewer 上次看到的那个具体交错",而不是"让所有交错都不可能的机制"。补丁在调用点加检查,每个检查点又成为新的竞态窗口——bug 空间随补丁数增长,循环永远追不上。

十轮母题归类(同一 bug 的十次变装):

| 轮 | 表面问题 | 母题 |
|---|---|---|
| R1 | 无证据判 interrupted;裸 catch 兜底 | 证据模型错 |
| R2 | stage 先推进、任务后 settle → 任务不可见 | 多事实源各执一词 |
| R3 | taskId 早于进程启动 + registry 空 → 推断已死 | 用缺失证明死亡 |
| R4-R6 | 面板/命令/服务端各自推导"当前任务是谁" | 多处重复推导 |
| R7-R8 | 校验只覆盖上轮被点名的分支/状态 | 不变量按样本打补丁 |
| R9-R10 | 迟到回调覆盖后继;check-then-write 不原子 | 写入无互斥、无原子性 |

R4-R8 是同一件事(重复推导不一致),R9-R10 是另一件事(写入无并发控制)浮出水面。**同类问题连续多轮复发 + diff 持续发散 = 修错了层面,必须停机重设计。**

## 代码级原则(六条,触发式)

### 1. 不变量先行

修任何状态/并发 bug 前,先写下不变量:谁拥有事实的唯一所有权?什么是原子提交单元?哪一代次持有写权限?查无记录能推出什么、不能推出什么?

答不出不变量 = 还没理解问题,**禁止动手写修复**。不变量写在修复 PR 的描述或 issue 评论里,让 review 可以对着它检查。

### 2. 构造优于纪律

在 N 个调用点插入"先检查再操作"不是修复,是登记债务:每个检查点本身就在竞态窗口里,且要求未来所有调用者记得做对。

判断一个修复的层次:
- **机制级**:不变量由类型、存储原语或串行化点强制,违反者写不出来。
- **调用点级**:靠每个调用处自觉 check。允许作为过渡,但必须登记收敛期限。

倾向前者的具体形态:把校验收进被调用的原语内部(而非调用方)、把所有权做进类型(非法状态不可表示)、单写者 + 原子提交。

### 3. 单一应答源

任何"当前 X 是哪个"的问题(当前任务、当前代次、当前分支、当前基线)全系统只允许一个应答源。面板、对话命令、API、后台回调一律消费同一引用,**禁止各自从 stage/历史/内存重新推导**。出现第二份推导逻辑 = 缺陷,即使当前两份恰好一致。

### 4. 写权限即凭证

变更共享持久状态的 API 必须在**签名上**要求代次/所有权凭证,校验发生在串行化临界区**内部**(先取得互斥,再读当前代次比对,再写),而不是临界区之前先 check 再写——后者只是把竞态窗口从"写之前"挪到"check 与写之间"。

反例(#111 R10):`saveCurrentTaskWorkflow` 先 load 校验、再用非原子 writeFile 覆盖,后继任务在两者之间落盘,旧回调 17% 概率覆盖新状态、11% 概率写坏文件。

### 5. 缺失 ≠ 死亡

内存表/registry 查无记录只能推出"当前控制器不可见"(unknown),不能推出"已终止"(interrupted)。unknown 必须 fail closed(禁止启动新任务以防双开),但**禁止宣判死亡**;只有明确证据(用户确认停止、进程退出码、supervisor 终态、超时)才允许写入终态结论。

禁止用任何单一信号冒充存活/死亡证明:PID 存在、日志时间戳新鲜、本地游标推进,都只是组合证据的一部分。

### 6. 对抗性验证与静态枚举审计

验证分两层,缺一不可:

- **静态枚举审计(先做)**:对每条不变量,grep 枚举全部可能违反它的代码路径(mutation API 的所有调用方、应答源的所有消费方、所有写入口),产出逐条打勾的枚举表。存在性缺口(哪些路径绕过了机制)是静态可枚举的,**必须一次找全**,一次找一个 = 跳过了这层。任何"靠调用点纪律"或"无保护"的行即为 finding,不需要动态复现。
- **动态对抗验证(后做)**:与实现同一心智模型的测试不是覆盖。并发修复的回归测试必须包含实现者**没想到的交错**:统计压测(高并发循环 + 失败率断言)、随机调度,或明确构造危险窗口(如"校验完成与写入之间插入后继写")。枚举表只证明路径覆盖,证明不了临界区内部逻辑与锁语义的正确。

纯函数输入输出测试证明不了跨实例、跨刷新、跨生命周期的正确性。CRITICAL 级 finding 的验证必须执行复现,不得只读代码推断;完备性的验收标准是**枚举表全部打勾**,不是"reviewer 没找到问题"。

## 流程元规则(两条,给循环)

### 7. diff 收敛律

连续修复轮的 diff 应收敛或稳定。修复轮持续净增代码(本例 93→885→1316→…→2669)= 在调用点层面堆补丁的确定性信号。review 见到发散趋势应升级处理,而不是继续逐条验证。

### 8. 同类停机律

同一母题的 CRITICAL 连续 ≥2 轮出现(本例 R7-R10 连续 4 轮),循环必须停止"逐条修复"模式,切换为"重设计轮":产出半页不变量文档 + 机制级方案,经确认后再实现。dev 侧不会自己喊停(它的激励是过本轮 review),停机判定必须在 review 侧。

## 机器门禁(已实现:`pnpm run check:state-writes`,AST 解析)

脚本 `scripts/check-state-writes.mjs` 基于 TypeScript Program + TypeChecker 做**符号级解析**(非文本正则、非名字集合):每个调用表达式解析到 state/workflow-persistence 的真实导出符号,别名链、命名空间属性、const/let 重绑定、赋值重绑定与解构均按 symbol 追踪。负向 fixture(`tests/check-state-writes-gate.test.ts`)锁定全部已知绕过路径——门禁自身也有必须失败的测试(名字追踪版本曾在两轮 review 中被绕过,故换范式)。已接入 `check` 复合链与 CI,执行原则 2/4 的三条边界规则:

1. **状态路径白名单**:workflow 状态文件路径(`workflowPath`/`workflowStatePath`)只允许在持久化层解析(`workflow-persistence.ts` 写入、`state-layout.ts` 定义、`state.ts` facade);其他文件触及即 CI 红。路径独占同时保证写入只能是持久化层的 temp + rename 原子写。
2. **持久化模块独占**:`workflow-persistence.ts` 只允许被 `state.ts`(facade)与 `task-ownership.ts`(纯选择器)import;上层直接 import 即 CI 红。
3. **条件提交**:任何 `saveWorkflow`/`saveWorkflowForTask`/`claimWorkflowTask`/`mutateWorkflowForTask` 的无 revision/凭证参数调用(单参数裸调用 = 无条件 last-writer-wins)即 CI 红。

## 适用范围

- **强制**:涉及共享可变状态、任务/进程生命周期、持久化文件、autoRun 控制器的修复与新功能。
- **参照**:纯展示、纯查询类改动可豁免原则 1-6,但原则 7-8(流程元规则)对所有 review 循环生效。

## 循环驱动模板

人工驱动循环时,输入可以只有一句:**「按 docs/fix-discipline.md〈某轮〉模板执行」**。场景由 review 判定决定(fix-these → 修复轮;stop-and-redesign → 重设计轮;新 issue → 新开发)。

### 新开发(首次开发,无 review 历史)

> 按 docs/fix-discipline.md 开发。若涉及共享状态、任务生命周期或持久化:先在 issue 评论写下不变量(原则 1)再动手写代码;实现优先机制级(原则 2/4,写权限即凭证);交付物包含受影响 mutation 路径的静态枚举表(原则 6)。纯展示/查询类改动可豁免原则 1-6。提交前自检:若发现自己在多个调用点插入相同检查,停下来换机制级方案。

### 修复轮(review 判定 = fix-these)

> 读 docs/fix-discipline.md 与本轮 review 后修复。先对每个 finding 判母题:若属于历史已复发母题,或唯一可行的修法是调用点级,禁止逐条修,按原则 8 报告需要重设计轮。单发新母题按原则 2 选机制级修法,并更新静态枚举表。本轮 diff 应净减少或持平(原则 7)。

### 重设计轮(review 判定 = stop-and-redesign)

> 重设计轮。先产出不变量文档,再按原则 2/4 实现条件提交:每条 workflow mutation 的签名要求 capability 或 expected revision,锁内重读-验证-变更-原子提交或拒绝;任务启动把 reservation + taskId + hostJobId + stage 建立为一次线性化迁移;移除所有无条件整对象写调用点。交付物必须包含静态枚举表:全部 mutation 路径逐条列出、逐条标注保护方式,表中不得有「调用点纪律」或「无保护」行。同步处理 review 指出的前瞻问题(如锁重入、错误语义混叠)。本轮 diff 允许净减少。

### 长期目标(状态:未实现)

模板的消费方最终应是 ClickVibe 自身的 prompt 构建(`src/agent/prompt.ts` 按 review verdict 自动选模板),人工输入退化为零;本文档是模板的唯一事实源,代码侧引用而非复制。

> 实现状态:**仅目标,未实现**。当前 `prompt.ts` 对 Review Meta 只做原文盲透传,不解析 verdict、不选模板。前置条件:① review skill 已要求 verdict 附「下一轮指令」段(已生效);② 待 #111 落地后独立小 PR 实现 prompt.ts 侧解析与模板注入。在落地前,人工输入「按 docs/fix-discipline.md〈某轮〉模板执行」仍是必需品。
