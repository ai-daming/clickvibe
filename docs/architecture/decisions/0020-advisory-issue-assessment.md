# ADR-0020：评估展示现状，用户决定开发

Status: Accepted（合入 main 后生效） | Work: #177 | Supersedes: [ADR-0019](0019-issue-implementation-gate-assessment.md) | Refines: [ADR-0012](0012-work-item-contract-canonicalization-and-evidence.md)

接受依据：维护者先明确“评估是为了把现在透明化，我们不应该挡住用户执意要做什么”，要求大幅简化，阅读本方案后确认“这个感觉还是可以的，按照这个继续”。接受不等于实现或现场验收完成。
核查基线：0169cdb1a1cba25a4d25703d45c386b4e2ee0600。
用户已确定方向：“评估是为了把现在透明化，我们不应该挡住用户执意要做什么”“要做大幅度的简化重构”。这取代旧方案把 READY 作为缺字段开发放行依据的产品方向。

## 1. 用户看到的流程

- 每张 Issue 保留开发入口。评估是独立可选动作，未评估、评估失败、报告过期、结论建议讨论，都不因评估状态禁用开发。
- 评估完成后展示原结论、理由和具体问题；有明确讨论事项则展示“继续讨论”。开发入口不消失，不要求勾选风险确认或取得 READY。
- 用户选择开发，把原 Issue 和可用评估报告交给开发 Agent；过期报告明确标注旧依据，没有报告就不附。评估建议不变成启动凭证。
- 用户选择讨论，沿用现有 Harness 会话桥带入 Issue 和问题；首版保持已讨论过的预填草稿行为。本次不混入自动发送的交互变更。草稿与导航失败分别报告，不把未发送说成已开始讨论。
- 整理讨论时默认回写原 Issue，沿用现有 gh-issue 的刷新、预览、已有授权和回读；成功后重新评估。不能把未确认建议写成用户决定。
- 单项、勾选批量、milestone 全部评估及可选自动触发共用同一条评估路径。自动默认关闭；启用后在所选项目列表使用期间触发，不另做常驻扫描服务。
- 批量是把固定目标逐项送入同一队列。逐项展示排队、进行中、结果或失败。重复目标复用已有任务或报告；不引入批次订阅、额度分摊和共享任务取消协议。
- 全部评估先完整枚举并显示数量，延续原已讨论范围，包括 CLOSED；这不自行重开已关闭的 Issue。

## 2. 明确删除

1. 单项/整批 token 额度、用量预算准入、超额模型拒绝、预算预留及分摊；不以另一个阈值替代。
2. 新增的单项/整批时间预算配置；正常调用失败、宿主取消和请求超时沿用已有行为，不新增用户需填写的预算表单。
3. 独立的模型策略、可信模型版本、改配置使旧报告失效的框架。复用 Harness 当前会话的模型选择，并将明确的 provider/model 与已有 reasoningEffort 传给后台 Agent；没有可用选择时，引导在现有 Harness 模型选择器中选择，不新增预算或完整模型设置页面。
4. READY 才允许开发的规则，以及 ADR-0019 §9 的 nonGoals/constraints 特殊豁免分支。不再为评估新建开发凭证或校验原始 READY receipt 才给开发权限。
5. 以评论已发布作为查看结果、继续讨论和开发的前置条件。
6. 每个批次独立预算、订阅、引用计数及取消传播。首版按 Issue 任务显示/控制，取消针对明确任务；不新增“取消整个批次”的复杂产品能力。
7. 评估专有发布许可管理界面和政策版本系统。点击评估包含对应报告评论发布，复用当前 GitHub 身份；不扩大到正文修改。
8. 把同机多实例支持发展成调度平台；复用现有互斥手段防止重复写/重复运行。

## 3. 保留的最小正确性

- 同一目标、同一依据已有运行时，不再启动第二个；旧运行晚到，不覆盖新依据。
- 固定评估读取的代码版本，记录 Issue 内容、代码与 skill 依据。相关变化标注旧报告需要更新，但旧报告仍可阅读和讨论，更不因此禁用开发。
- 普通评论、验收勾选、无关元数据变化不触发重算。代码版本变化按 skill 核验规则处理，不谎称旧回执在新 SHA 仍有效；区分历史报告可读与结论是否已针对新版本复核。
- 评估 Agent 只读，使用现有 Harness 创建、会话记录、完成和取消能力；不模拟输入框，不另造 Agent 运行时。
- 完整 skill 及必需引用可用；必要证据读不到就说明缺什么，不伪造结论。
- 结果先保存本地，再尝试评论发布。评论失败独立显示，不重跑分析；结果不丢。
- 评论发布结果未知时先核对已有记录，不能盲目重复发布。复用既有 GitHub Gateway 的写后回读能力，只补任务对应标记和恢复路径。
- 重启复用完成报告；排队任务按已接受清单恢复。运行中的任务从宿主持久记录核对，查不清显示中断，不猜成功。显式重试可重新评估。
- 发布身份、内容和来源供报告归属核对；未经验证的外来评论不冒充本机评估结果，更不影响开发授权。
- 所有失败留原始原因并可见，不把失败、缺记录或解析不了写成“已交付”。

## 4. 最小数据与行为对应

数据优先引用 Harness 已有会话和日志，不复制聊天内容。沿用已有 active-root 写守卫、文件锁与完整写入原语，不改变工作流 schema 和 canonical 指纹。

| 记录 | 为什么保存 | 谁使用 |
|---|---|---|
| 每次评估的 Issue 身份、依据、任务/会话标识和运行结果 | 防重复、恢复、定位报告属于谁 | 评估执行与列表展示 |
| 原始报告或完整报告引用 | 重启可读，不因发布失败重算 | 展示、讨论、开发上下文 |
| 评论发布标记、评论编号和错误 | 区分分析完成与保存到 GitHub 完成 | 发布回读与恢复 |
| 项目自动开关；宿主确需的最小模型选择 | 确定哪些项目触发、如何运行 | 入队和宿主调用 |
| 讨论会话与原 Issue 的关联 | 讨论后准确回写原目标 | 整理 Issue |

不新增独立“当前 READY 权威指针”。当前展示从目标依据及评估记录推导。批量进度由目标对应任务计算，不存第二份成功结论。

| 动作 | 处理 | 失败后的行为 |
|---|---|---|
| 评估 | 获取依据；复用结果/运行，否则记录任务再排队 | 显示读取或启动失败，开发仍可选 |
| 评估完成 | 核对对应会话完成事实，保存报告 | 不完整输出显示失败，不报 READY |
| 发布评论 | 保存报告对应发布信息，经 Gateway 写后回读 | 本地结果继续可读；未知结果只核对，不盲目重发 |
| 开发 | 沿用动作授权和任务保护，附 Issue 与评估上下文 | 真实执行错误如实处理；评估 verdict 不参与拒绝 |
| 讨论回写 | 绑定原 Issue，刷新后按已授权变更写入，回读后重评 | 不覆盖并发修改，不冒充回写成功 |

## 5. 现有拦截必须一起改

静态枚举发现 contractHasKnownCanonicalFields 的生产调用位于六处：
- src/workflow/merge.ts：develop/auto 动作授权。
- src/workflow/develop-start.ts：真正启动开发前。
- src/workflow/prompt-resolution.ts：Agent 输入准备。
- src/workflow/create-pr.ts：创建 PR 前。
- src/workflow/merge-gates.ts：fetchIssueContract，被 review 等流程读取。
- src/workflow/auto-run.ts：自动运行路径。

不能把该函数直接改成恒 true。必须把两类情况分开：
1. 已成功读取 Issue，但内容缺章节、描述冲突或不符合解析格式：保留原文与缺口，供评估/Agent 理解；不因描述质量拒绝用户明确选择的开发。unknown 保持原值，指纹算法不变。
2. 无法识别目标、没有取得数据、记录格式版本不支持或文件损坏：这是无法可靠执行，不能伪装成“用户选择忽略评估”。仍显示实际故障。

页面按钮、手动选择和后端实际启动要一致；自动替用户挑选任务与用户明确选择开发不同，不借这次改动擅自启动用户没有选择的工作。

允许尝试开发不代表自动通过验收。创建 PR/启动 review 不应因为缺模板章节而拒绝；review 仍如实说明无法验证的事项。合并权限、真实 Git 冲突、任务占用、原有 review 证据与合并策略不因评估改造被绕过。共享读取函数的变更必须检查 merge 消费方，防止意外放宽自动合并。

## 6. 对旧设计的替代与验证

本 ADR 替代 ADR-0019 的完整评估方案，取消其预算、批次订阅及报告授权绑定；ADR-0012 关于 canonical 字段 unknown 的执行边界按下节明确修订。#177 的旧“待决问题”和设计阶段记录应按本 ADR 更新，不能把旧记录当成尚未决定的需求。旧设计尚无 #177 实现，不需要迁移不存在的评估数据。

重点验收：
- 未评估、评估失败、过期、建议讨论四种情况下，用户均可明确选择开发；无额外 READY/风险确认表单。
- UI 能点且后端能启动，不在提示词、PR 或 review 准備处因同一描述缺口再次卡住。
- 真实任务占用、数据读取损坏与未经授权的执行仍不被绕过；允许开发不制造自动验收通过。
- 重启复用结果、重复点击不重复运行；评论发布失败仍能查看/讨论；回写目标正确。
- 单项/批量/全部/自动共用路径；不出现 token 额度或强制预算配置。

## 7. 收口后的执行与存储契约

### Harness 与模型

静态核查 Harness `aa8262ec091698bae9a6b04773a6b5b06ad4aef2`：`modelDirectories.directoryFor(sessionId).load()` 返回该会话目录及 current；`ctx.agents.create` 接收显式 agentOptions；`agent.ts:prepareRequest` 不会为省略的 provider/model 自动选当前聊天路由。

手动入口从当前普通 Harness 会话取得明确模型选择，传入评估请求；服务端核对路由可用。开启项目自动评估时保存同一选择供后台使用，运行记录保留实际来源。仅保存 provider/model/已有 reasoningEffort，不复制供应商配置或凭据；切换模型不使旧报告自动作废。无会话选择时引导用户使用现有模型选择器；不猜模型。宿主接口不可用只影响评估，开发入口不依赖它。

每次评估仍为独立只读 root Agent。setup 中限制全局工具，并用现有 scoped tools.guard 拒绝非评估读取工具，覆盖后来注册的 scoped 工具；禁止以提示词代替权限。读取固定 Git 对象和目标 Issue，不暴露私人文件。使用完整 impl-gate 与 references；保留其原始 verdict、解释与可有的回执，但回执不参与 ClickVibe 开发授权。必要外部证据当前读取能力不支持时报告缺失，不伪造。

### 最小持久状态

active root 下 `assessments/state.json`（schema=1）只含 revision、projectSettings、runs、discussions；报告单独存不可变文件。不保留 requests、批次订阅、token 计量、许可策略版本、独立 READY 指针。projectSettings 只保存自动开关及所用宿主模型选择。

run 保存 runId、Issue 身份、评估依据、会话/消息标识、执行者、执行状态、报告引用、发布信息和最近错误。执行状态只有 queued/running/completed/failed/interrupted/cancelled；过期由当前依据比较得出。评论保存状态独立为 pending/published/unknown/failed，不乘成一套总状态。completed 表示分析完成，不表示结论 READY 或开发已交付。

所有入口经同一个存储锁提交：先完整读取目标与依据，再在锁内去重和一次保存全部待评估目标，然后应答；枚举不完整则不把部分目标称为全部。同 Issue 同依据的 queued/running 或当前完成报告复用，不新增订阅。每个新任务记明确顺序，单协调器按保存顺序逐个执行；用户查看批量进度只需读取返回的目标与 runId，不新增批次持久实体。浏览器关闭不丢已经提交的队列。

领取任务在锁内检查 queued 及现有执行者，只允许一个 running，保存本次执行者和预分配会话/消息标识后才调用宿主。锁在外部调用前释放，所有回调带 runId 与执行者身份回到同一个锁内核对。复用现有跨进程锁与运行者生存核查；不能确认运行者已停止时不抢占。新依据另记新任务，旧结果保留自己的依据，展示只比较当前输入，不让迟到结果覆盖新记录。

报告先完整写入并回读，再在锁内记录 completed 及引用。取消只针对 UI 明示的 Issue 任务；queued 可直接取消，running 由宿主取消并按实际终态记录。任务已完成时保留报告。没有批次级取消，更没有因为一个页面离开而取消其他人看到的任务。错误通过现有诊断写入并显示。

重启时 queued 继续调度；completed 复用；running 查自身消息的持久结果，能证明完整结束则补存报告，否则在确认无活跃运行者后记 interrupted，不因缺记录推断成功。缺失/未知格式只禁用评估记录写入，不损坏业务 workflow。

发布在本地完成之后：锁内保存唯一 run marker、固定正文摘要与当前 GitHub 发布身份，再经既有 Gateway 发起一次写入。收到响应后回读相同评论；结果未知只按 ID 或 marker 核对完整分页，不盲目再次 POST，不因发布失败调用模型。已分析报告始终可查看、讨论和作为带来源的开发上下文。评论来源不明时仅作历史文字，不导入成可信本机运行事实。未知发布结果不阻塞其他 Issue 的模型评估。

### 开发和合并的准确边界

ADR-0012 §2、§5、§8 的“字段 unknown 必须停止”不再适用于用户明确选择的 develop/auto 启动、后续提示词准备、创建 PR 或启动 review。原始字段仍保存 unknown，缺口随原文传给 Agent；不通过补造空值或修改 fingerprint 使其看似完整。

`fetchIssueContract` 应能返回成功读取但字段不完整的契约；原先隐含在此共享读取函数内的合并完整性检查移到合并门禁调用侧，保持既有 merge 策略和人工 override 通道。缺模板字段不等于读取失败，两者错误原因必须分开。review 可以运行并报告验收依据不足，不能把不足的证据自动转为通过。

权限和时效检查仍绑定最新原始 Issue、契约指纹和任务版本，避免用户点击后悄悄换目标；不新增“我确认风险”授权类别或额外弹窗。用户明确选择“自动跑到底”可开始执行，但不因此放宽后续自动合并门禁。自动推荐/自动选取仍可按准备情况筛选，不能隐藏用户直接选择开发的入口。

这次修改的是 ClickVibe 的产品门禁。impl-gate skill 对执行它的 Coding Agent 的指导并不被改写；未满足的设计/决策仍在报告中明示，不宣称点击开发保证 Agent 一定完成交付，也不通过隐藏问题让 Agent 编造决定。

## 8. 生效、回退与交付

ADR-0019 转为 Superseded；ADR-0012、架构入口和索引在同一设计变更中更新。本设计生效后对该 exact main SHA 再执行 impl-gate，才进入实现。旧 #177 只有文档没有评估数据，故无需迁移尚不存在的 schema；原有 workflow/config/canonical 格式保持。

回退插件时旧版本忽略评估目录，可能恢复旧的缺字段开发拦截；不删除评估历史，不伪称回退后用户仍可执行新入口。实现/测试由本任务承担；合入不等于上线，运行环境仍由维护者前台启动。人工端到端验收按 #177 现有 AC 在实现和工程检查完成后集中执行，真实外部测试目标使用前确认，不把未执行验收标成已完成。

交付必须证明第 6 节的行为以及模型来源和只读执行实际成立。模型调用和服务控制不因设计接受而自动获得现场权限。开发前核验、独立 review 与实际验收各自记录，不把文档合并当作功能完成。
