# ClickVibe Issue 契约:可自动开发的 issue 写法

> 配套 [product-blueprint.md](product-blueprint.md) §"自动化边界"与 [ADR-0003](architecture/decisions/0003-issue-architecture-gate.md)。目标:让 issue 能被 ClickVibe 自动选取、完成架构分流、开发和 review，同时不加重业务提单负担。

## 核心原则

**三个环节,各只需一个必读项:**

| 环节 | 必读项 | 缺了会怎样 |
|---|---|---|
| 自动选取 | **依赖**(Blocked by #NN / 无) | 可能选了被阻塞的 issue |
| 自动开发 | **目标**(做什么) | agent 自己脑补,风险最大 |
| 自动 review | **验收标准**(可判定 check) | 没有判据,通过/失败靠猜 |

## 最小集合(3 项必填)

日常 issue 只需三行:

```markdown
## 目标
一句话说明要做什么。

## 验收标准
- [ ] 一条可判定的检查(能明确说"通过/不通过"的行为或测试)

## 依赖
无  或  Blocked by #NN
```

**30 秒可提一个可自动开发的 issue。**

这里的“可提单”不等于“可以直接 coding”。Issue 进入 ready 队列前还必须完成一次架构影响判定；这个判定属于工程分流，可以由维护者或架构 Agent 补充，不要求业务提单人预先编写实现方案。

## 架构影响判定(coding 前必需)

| 等级 | 判断 | 进入 coding 前的要求 |
|---|---|---|
| L0 | 文案、样式、局部纯逻辑 | 遵守现有架构，直接开发 |
| L1 | 单模块行为变化 | 写明数据来源、状态与失败路径 |
| L2 | 跨模块、API、缓存、Git/GitHub I/O | 先形成设计或 ADR，并绑定 Accepted baseline |
| L3 | 并发、持久化、权限、自动合并、共享状态 | 先定义事实源、不变量、原子边界、失败模式、迁移与回滚 |

无法确定等级时不得默认降级，标记 `architecture-review-required`。L2/L3 的设计应先通过独立 PR 合入 baseline，再让实现 Issue 开始并行施工。

## 可选增强(有则更好,缺了不卡)

| 项 | 何时值得写 | 缺失后果 |
|---|---|---|
| **约束/边界** | 有明确"不要做 X"的边界 | agent 可能多做,review 能兜住(风险中) |
| **入口** | 测试/运行命令特殊,agent 找不到 | agent 自己读 package.json/README,慢但不卡 |

```markdown
## 约束
不要改动 X 模块;不要自动重发非幂等消息。

## 入口
运行 `pnpm test` 验证;本地起 `go run ./cmd/afu` 复现。
```

## 分级模板

按 issue 复杂度选择,不必每次都写全:

```
简单(一行):  目标一句 + 验收一条
  "给欢迎语加重试,失败 3 次后标记 failed。验收:重试次数可配且日志可见。"

标准(三行):  目标 + 验收 + 依赖
  简单版 + "依赖:无"

完整(复杂):  目标 + 验收 + 依赖 + 约束 + 入口(必要时加 关联/问题/非目标)
  参考 afu #103 的全格式(关联/问题/目标/实现要求/验收标准/非目标)。
```

## 验收标准怎么写才"可自动判定"

- ✅ 好:行为或测试,机器/agent 能验证
  `- [ ] 重试 3 次后状态标记为 failed 且日志输出原因码`
- ❌ 模糊:无法判定
  `- [ ] 功能正常` / `- [ ] 处理好各种情况`

## 验收条款的验证方式与"谁勾"

每条验收可加一个验证方式前缀,决定**谁能勾掉它**:

| 前缀 | 谁勾 | 例 |
|---|---|---|
| (缺省,不写) | agent(review 时自动验证) | `- [ ] 重试 3 次后状态标记为 failed` |
| `[人工]` | 只能用户勾,agent 禁止代勾 | `- [ ] [人工] 逐步操作录入 50 条手感正常` |
| `[外部]` | 只能用户凭外部证据勾 | `- [ ] [外部] 发布审批已过(附链接)` |

- **缺省 = 自动**,30 秒提 issue 的承诺不变;只有"必须人来验"的项才写前缀。
- review 时:**agent 只能勾自动项**;`[人工]` / `[外部]` 项未勾不算通过。它们阻止自动合并，直到用户补充外部证据或明确决策；merge 本身是否自动由项目/任务策略决定。
- 没写前缀的项一律按自动处理,不允许 agent 仅凭"代码/测试通过"把人工项算完成。

## 机器可读约定(自动选取用)

- **依赖**:固定写 `依赖: 无` 或 `依赖: Blocked by #NN`(多依赖逗号分隔),不要散在正文
  - **只写直接前置依赖**:A→B→C 只记 B 被 A 阻塞、C 被 B 阻塞,不冗余写 C 被 A 阻塞;自动选取**不计算传递依赖**,避免误判就绪/误判阻塞
  - 有原生支持时优先用 GitHub **原生 Blocked by 关系**(可回读验证、跨机器一致);正文写法保留为降级兜底
- **状态 label**(可选):`ready` / `blocked` / `wip` 帮助自动选取跳过非 ready
- 验收标准统一用 `- [ ]` checklist,ClickVibe 以"全勾 = 通过"为 review 判据;每条按"验证方式"区分谁能勾

## ClickVibe 侧的支持(待实现)

- 提 issue 时给出**最小模板引导**(三个空:目标/验收/依赖)
- 自动选取前**校验契约**:缺依赖/验收 → 提示补齐,不硬选;就绪判定只按**直接前置依赖**
- 进入 coding 前校验**架构影响等级**:L2/L3 缺 Accepted 设计/ADR → 保持未就绪，不把业务 Issue 直接喂给 Coding Agent
- review 时以验收 checklist 为判据,非空泛判断;只勾自动项,`[人工]`/`[外部]` 未勾不通过
- review 结论**绑定契约指纹**(目标/验收正文指纹)+ PR head;正文目标/验收被改 → 结论过期 → 重新 review(细则见 [state-model.md](state-model.md))
- 自动写动作(建 PR/发评论/更新状态)执行后**回读 GitHub 验证落盘**,不轻信零退出码;失败本地事件照记,状态不倒退
